# DART 개발 작업 규칙

목적은 팀원 변경을 놓치지 않고 작은 단위로 개발하며, 공동 회고에 넣을 채은의 작업 내용을 짧게 제공하는 것이다. 사용자 지시가 이 규칙보다 우선한다.

## 프로젝트 기준

- Git 루트의 `docs/development-plan.md`를 기준으로 구현한다. 제안 설계를 확정 요구사항으로 바꾸지 않는다.
- 채은은 서비스 구조·UI, 상협은 Studio Agent 고도화를 맡는다. Agent 스키마 변경은 협업 접점으로 기록한다.
- 현재 브랜치는 `production-transition`. 브랜치를 새로 만들 때도 사용자가 요청하지 않은 `codex/` 접두사를 붙이지 않는다.
- 경로는 실행 환경의 cwd만 믿지 말고 `git rev-parse --show-toplevel`로 확인한다. worktree를 보통 폴더처럼 복사·이동하지 않는다.

## 작업 시작: Git 확인과 가져오기

1. 현재 브랜치·`git status --short`·원격 URL·upstream을 확인한다. 기존 미커밋 변경의 소유 범위를 파악한다.
2. `git fetch origin`으로 최신 원격 참조를 가져온다. 실패하면 환경의 승인 절차로 재시도하고, 확인하지 못한 원격을 최신이라고 말하지 않는다.
3. 현재 브랜치의 원격 upstream과 `origin/main`, 필요 시 `origin/sanghyeob`의 새 커밋·변경 파일을 확인한다. upstream이 없으면 같은 이름의 원격 브랜치 존재 여부부터 확인한다.
4. 연결된 원격 작업 브랜치가 있고 fast-forward 가능한 새 커밋이면, 미커밋 변경을 보호한 상태에서 `git merge --ff-only <upstream>`으로 반영한다. 로컬 main은 다른 worktree에서 사용 중일 수 있으므로 전환하지 않는다.
5. `origin/main`의 미반영 변경은 작업 브랜치에 필요한 내용을 검토해 통합한다. fast-forward가 불가능하면 변경 목적과 현재 작업을 확인한 뒤 일반 병합으로 반영한다. 팀원 미완성 브랜치를 매번 자동 병합하지 않는다. 이번 작업에 필요한 팀원 기능이면 검토·통합한다.
6. 미커밋 변경과 통합 대상이 겹치면 사용자 변경을 덮어쓰거나 자동 stash·reset하지 않는다. 이번 작업의 완료된 변경만 먼저 커밋할 수 있으면 그렇게 진행한다. 소유자가 불명확한 충돌은 상황을 설명하고 필요한 결정을 요청한다.

원격 검토 결과는 새 변경의 핵심과 반영 여부만 짧게 알린다. 원격 동기화는 코드 수정 전에 수행하며, 확인 결과를 이미 얻은 같은 세부 작업에서 이유 없이 반복하지 않는다.

## 작업 시작: 회고에 넣을 내용 출력

- 새로운 작업일 또는 사용자가 작업 시작을 요청한 시점에 [회고 작성 기준](references/daily-report.md)을 적용한다.
- 오늘 목표·예정 체크리스트·채은 역할 중 필요한 항목만 짧게 출력한다. 같은 날 기능마다 전체 시작 회고를 반복하지 않는다.
- Google 문서는 직접 수정하지 않는다. 사용자가 복사해서 입력한다. 문서 입력을 위한 재승인도 요청하지 않는다.
- 현재 시점의 계획으로 표현한다. 이미 끝난 일을 작업 전 목표였던 것처럼 날짜·시각을 소급해 쓰지 않는다.

## 세부 작업과 커밋

한 기능, 독립된 오류 수정, 하나의 문서·설정 정리처럼 설명·검토 가능한 단위로 작업한다. 매 파일 저장이나 매 도구 호출마다 커밋하지 않는다.

각 단위가 완료되면:

1. 변경 범위와 관련 검증을 확인한다. 코드에는 필요한 테스트·실행 확인을 수행하고, 문서·스킬에는 내용·링크·형식 또는 제공된 검증 도구를 사용한다. 실패를 숨기거나 통과했다고 기록하지 않는다.
2. `git diff`와 미추적 파일을 검토한다. 이번 단위의 파일만 명시적으로 stage한다. 기존 사용자 변경, API 키·`.env`·CV·업로드 원문·실행 결과를 일괄 stage하지 않는다.
3. stage된 차이를 확인하고 로컬 커밋한다. 완료한 세부 작업을 하루 종료까지 모두 쌓아두지 않는다.
4. 제목은 짧은 한국어 동작·핵심 변경으로 작성한다. `codex`, AI 표시, 이모지, 자동 생성 문구를 제목에 넣지 않는다. 예: `구글 로그인 연결`, `기업 비교 화면 추가`, `CV 삭제 처리 수정`.
5. 커밋 해시·핵심 변경·검증 결과를 기록하고 미커밋 변경이 남았는지 확인한다. push·PR·배포는 별도 사용자 요청이나 기존 승인 범위에 따라 수행한다. 로컬 커밋을 GitHub 반영으로 표현하지 않는다.

검증 실패나 의도하지 않은 변경 때문에 완료하지 못한 단위는 완료 커밋으로 포장하지 않는다. 현재 상태와 남은 검증을 알린다. 커밋 자체가 막히면 작업을 보존하고 이유를 보고한다.

## 작업 종료와 인수인계

- 사용자가 오늘 작업 종료·마감·회고를 요청하거나 하루 개발 세션을 마무리할 때 회고 작성 기준으로 종료 문구를 출력한다. 중간 질문을 하루 종료로 취급하지 않는다.
- 현재 세부 작업이 완료됐으면 해당 단위의 커밋을 먼저 마친다. push를 안 했으면 GitHub 커밋 링크를 만들어내지 않는다.
- 회고는 목표와 실제 결과를 구분하고, 실행한 검증·만든 산출물만 반영한다. 작성하지 않은 팀원 항목은 비워둔다.
- 인수인계에는 실제 작업 브랜치, 마지막 커밋, 미완료 작업과 다음 첫 행동을 짧게 남긴다. 이미 있는 일일 기록이 있으면 중복 문서를 만들기보다 갱신한다.
- 스키마·실행법·개발 범위가 달라졌으면 관련 명세나 README도 같은 작업 단위에서 갱신한다. 코드가 없는 문서 작업에 불필요한 테스트·인프라 작업을 추가하지 않는다.

## 실행 경계

이 스킬은 정기 실행 예약, 팀원 메시지 전송, Google 문서 편집, 자동 push를 지시하지 않는다. 로컬 개발과 회고 문구 출력을 위한 규칙이다.
